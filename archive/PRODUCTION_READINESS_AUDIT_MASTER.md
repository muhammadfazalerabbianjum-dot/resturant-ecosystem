**P1-STATE-A — unguarded async `setState` in the owner dashboard (the exact crash class this audit exists for).** `owner_dashboard.dart:390-402`: `onPressed: () async { await adminService.updateUserBranch(user.id, selectedId); setState(() { final idx = _users.indexWhere(...); ... }); ...` — no `mounted` check after the await and no try/catch. If the dashboard is disposed while `updateUserBranch` is in flight (user pops the screen/navigates from behind the sheet), this throws `setState() called after dispose()`. **P1-GPS — `DriverLocationService.startTracking` leaks the previous geolocation subscription.** `driver_location_service.dart:72-77`: `_positionStream = Geolocator.getPositionStream(...).listen(...)` reassigns without cancelling a prior subscription. The delivery dashboard offers a GPS button per `pickedUp` order (`delivery_dashboard.dart:244-254`) and gating is status-chip-only (no in-flight lock), so a double-tap — or starting order B before Firestore streams back order A's status flip — orphans the first stream: two live `Position` listeners both calling `_publishLocation`, which now targets the single mutable `_activeOrderId` (83) → duplicate `deliveries/{id}` writes, doubled GPS/battery cost on driver devices, and stale-listener writes continue until process death. `stopTracking` (113-118) is only called on the delivered paths, not on re-start.

**P1-TRANSITION — order-status writes have no transition validation (state-machine integrity gap).** `KitchenService.updateOrderStatus` writes any status unconditionally (`kitchen_service.dart:41-51`), `DeliveryService.markDelivered` unconditionally stamps `delivered` (`delivery_service.dart:66-77`), and even the transaction-guarded `assignToMe` (81-101 — the file's own best practice) validates only `assignedDriverId`, not current status, so an unassigned `delivered`/`cancelled` order could be flipped to `pickedUp`. UI gating exists (`kitchen_dashboard.dart:182-183` `canStart`/`canReady`; delivery status chips) but it is stale-prone: two kitchen tablets, or kitchen + delivery dashboards, act on asynchronous snapshots — a stream that has not yet delivered the `cancelled` emitted by the abandonment flow lets a chef confirm→prepare a dead order; a driver can mark `delivered` an order concurrently re-flipped by staff. There is no `canTransitionTo` on `OrderStatus` (`order_model.dart:9-27` — the enum owns normalisation but not the machine). Firestore `status` rules/CF enforcement is section 09/02 territory; the **client-boundary** guard specified below is this section's scope.

**P2-STREAM-BUILD — Firestore streams constructed inside `build()` cause listener churn on every rebuild.** `kitchen_dashboard.dart:140-142` and `301-305` (the latter also `ref.watch(restaurantConfigProvider)`, so the config resolving from loading→data guarantees ≥1 rebuild→resubscribe), `revenue_chart_widget.dart:25-34` (same config-watch + query built per build), `admin_reservations_tab.dart:50-53`. Every rebuild passes a **new** stream instance to `StreamBuilder` → unsubscribe + resubscribe: redundant Firestore snapshot registrations (Spark-plan read cost), transient stale windows, and one extra full snapshot per rebuild. The codebase already contains the correct pattern one screen away: `delivery_dashboard.dart:196` watches `myOrdersProvider(driverUid)` (family StreamProvider — `delivery_service.dart:28-43`) instead of building streams in build.

**P2-CART-DIVERGENCE — optimistic cart state is not reconciled when persistence fails.** `cart_provider.dart:66-68` (`addItem`, same shape in `removeItem`/`clearCart`): `state = AsyncValue.data(newCart);` **then** `await _repo.saveCart(newCart);` — and `CartRepository.saveCart` rethrows on Isar failure (`cart_repository.dart:85-88`). On a failed write (disk full, DB locked), the in-memory cart keeps the mutation while the durable cart does not; the error surfaces only as a generic `addToCartFailed` snackbar, and after app restart `loadCart()` silently resurrects the old cart — items the user believes are saved vanish. Violates the codebase's own Offline-First law (the sync-queue pattern used for orders is not applied to the cart, and no revert/retry bridges the gap).

**P2-GUARD-DUPLICATION — two live `ForceUpdateGuard` implementations; the wired one is the less capable copy.** `packages/core_ui/lib/src/config/force_update_guard.dart:10-60` defines the DI-friendly contract (`ForceUpdateChecker` + fail-open `_FailOpenForceUpdateChecker`) yet `main.dart:16` **hides** it (`import 'package:core_ui/core_ui.dart' hide GdprConsentDialog, ForceUpdateGuard;`) and `main.dart:18,252` wires the parallel local copy `labs/app/config/force_update_guard.dart:10,20`. Two implementations of a kill-switch widget will drift (update-dialog copy, store URLs, recheck policy); the package one is dead code despite being the contract-designed version. White-label blast radius: generated shells inheriting the labs copy silently miss any future hardening done in core_ui (audit-08 interlock).

**P3-MSG-LOSS — cart business-rule exceptions collapse into a generic message.** `cart_provider.dart:51-54,58-62` throw descriptive limit exceptions ("Inventory limit reached…", "Cart capacity limit…"); `dish_detail_screen.dart:44-57` catches everything → single `loc.addToCartFailed` snackbar. The user is never told *why*; fix is a typed result/exception → localized copy.

**P3-ISAR-HALF-SINGLETON — `IsarService` exposes both an unused private singleton and a public per-call constructor** (`isar_service.dart:7-30`). Verified **safe today**: every instance's `openDB()` checks `Isar.instanceNames.isEmpty` and returns `Isar.getInstance()` (41-57), so no duplicate DB handles — but the `_instance`/`IsarService.instance` path is vestigial and invites future divergence; unify on one construction path.
