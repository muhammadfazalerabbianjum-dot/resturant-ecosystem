## 2. The white-label factory works (this is the strongest part of the repo)

- `apps/halal_boyz` is 7 Dart files. `lib/main.dart` calls
  `initCarnamaApp(CarnamaBootstrap(...))` from `package:labs`;
  `lib/app/app.dart` returns `const CoreApp()`. There is no forked app body.
- `core_app/lib/app_bootstrap.dart` owns the whole boot: a documented 16-step
  chain (fail-fast demo guard → FCM background handler → error widget →
  `PlatformDispatcher.onError` → bindings → dotenv → `AppConfig.loadConfig`
  → fonts → `CoreConfigHolder` → logger → config-failure surfacing →
  schema gate → Firebase key gate → Firebase init chain → Isar → navigation
  bridge + `runApp`). Fleet apps differ only in their inputs
  (`firebaseOptions`, `coreConfig`, `appBuilder`, `loadEnv`,
  `firebaseErrorScreenBuilder`).
- `core_app/tool/whitelabel.dart` (4,863 lines) is a real generator:
  `--config`, `--template`, `--dry-run`, `--regenerate`, `--allow-usd-fallback`,
  `--skip-firebase`. It validates the config, then emits a shell app plus a
  per-client `backend/` (`firestore.rules`, `storage.rules`,
  `firestore.indexes.json`, `.firebaserc`, `firebase.json`, `DEPLOY.md`).
  Post-gates: branding tools (exit 75), `flutter test` (72),
  `flutter build apk --debug` (73), flutterfire fail-closed (74).
- Per-client backend `firebase.json` points functions at the **shared**
  `../../core_app/functions` source — functions are not forked per client.
  Rules and indexes **are** copied per client.
- Each client is its own Firebase project (`demo-tenant` for Halal Boyz).
  There is no shared multi-tenant database.

Consequence: "one backend, many surfaces" is per-client. Roles, branches,
ledger and inventory all live inside each client's project. "Multi-branch" is
intra-project. "Multi-tenant SaaS" is a different product that this repo does
not currently implement.

## 3. Identity: one role, one branch, one owner

- `packages/core/lib/src/auth/user_model.dart`:
  `enum UserRole { owner, manager, kitchen, delivery, customer }`.
  `UserRoleConverter` falls back to `customer` on anything unknown.
- `UserModel` carries a **single** `role` string and a **single** `branchId`.
  There is no `counter`, no `waiter`, no role list, no branch list.
- `familyName/role` is denormalised into the JWT custom claim by the
  `syncUserRoleClaims` trigger in `core_app/functions/src/index.ts`, which
  writes one `role` claim.
- `core_app/functions/src/access.ts`:
  `STAFF_ROLES = ['owner','manager','kitchen','delivery']` and
  `assertStaffRole()` fails closed on the JWT claim. This is the only
  shared server-side role gate; individual callables otherwise guard ad hoc.
- Owner identity is `settings/ownerInfo.ownerEmail`, compared to the token
  email by `isOwner()` in `core_app/firestore.rules`. Exactly one owner
  identity exists per project; a second owner is not expressible.

## 4. Access control today

- `core_app/firestore.rules` (811 lines) is the real authority for direct
  client reads/writes. Patterns:
  - `userRole()` / `userBranch()` read `users/{uid}` with `get()` inside the
    rule (a document read per evaluation).
  - Order updates are **per-role allowlists** with shape locks:
    `affectedKeys().hasOnly([...])` — kitchen `['status','updatedAt']`,
    manager `['status','assignedDriverId','updatedAt']`.
  - `audit_log` / `audit_logs` writes are `false` (Cloud-Functions only).
  - The `orders` create allowlist has no `channel`, `tableId`, `staffId` or
    payment-method field; `orderSource` is server-owned.
- Consequence for this project: item-level ready flags, per-line state,
  payments and ledger rows **cannot** be expressed as client-writable
  `hasOnly([...])` shape locks without combinatorial growth. Order mutation
  authority has to move into callables.

## 5. Money path (server-authoritative — keep it)

- `createPaymentIntent` → `createChargeIntentCore` (`index.ts`, seam at
  `CreateChargeIntentStripeSeam`): re-prices every line from `menus`
  (`verifyMenuPricing`), derives tax/promo/currency server-side
  (`resolveChargeTaxAndPromo`), clamps the delivery fee against
  `settings/restaurantConfig`, builds one metadata bag via
  `buildChargeIntentMetadata` (`createdBy` is always `request.auth.uid`),
  creates the PaymentIntent with `automatic_payment_methods` and an
  idempotency key, and only then commits promo usage.
- `createOrder` requires a **succeeded** PaymentIntent whose metadata
  `createdBy === uid`, re-verifies money against the intent, and stamps
  `customerId: request.auth.uid`.
- Therefore **there is no staff-created, cash, walk-in or phone order path**
  in the product today. This is the single hard blocker for counter and waiter.

## 6. Order model and lifecycle

- `core_app/lib/features/orders/domain/order_model.dart`:
  `OrderStatus { pending, confirmed, preparing, cooking, ready, pickedUp,
  delivered, cancelled }` with a `canTransitionTo` state machine.
  No `open`/tab state, no `delayed`, no per-item state, no `channel`,
  no `tableId`, no `staffId`, no `paymentMethod`.
- `core_app/lib/features/admin/domain/kitchen_service.dart`:
  `streamOrders(branchId, statuses)` ordered by `createdAt`, capped at
  `kKitchenOrdersStreamCap = 200`; `updateOrderStatus` runs a transaction then
  enqueues a `SyncQueue` payload built by `buildKitchenStatusUpdatePayload`
  to exactly `{id, status}`.
- `core_app/lib/features/admin/domain/analytics_provider.dart`:
  `fetchTodayAnalytics` uses a Firestore aggregate (`sum('totalCents')` +
  `count()`); `fetchTopDishes` groups client-side over
  `kAnalyticsTopDishesQueryCap = 200`. No channel dimension, no branch
  breakdown, no time-series, no server rollup.
- `core_app/firestore.indexes.json` already contains the composite indexes a
  kitchen queue needs (`branchId + status + createdAt`, both directions),
  plus presence, menus, reservations, waitlist and carts composites.

## 7. Real-time and presence (no new transport needed)

- "Real-time" is Firestore `snapshots()` listeners. Kitchen listens to the
  branch order queue; live tracking is `deliveries/{orderId}` documents.
  There is no socket server, no SignalR/Pusher, no Pub/Sub-to-client hop.
- `packages/core/lib/src/presence/presence_service.dart` maintains
  `presence/{uid} = {isOnline, lastSeen, branchId, role}`, driven by
  `WidgetsBindingObserver`, injected from the DI graph, and only for staff
  with a non-empty `branchId`. A composite index for
  `presence (branchId, isOnline, lastSeen)` already exists in
  `core_app/firestore.indexes.json`.
- Scale judgement (single branch, tens of concurrent listeners, hundreds of
  order events per day) is comfortably inside Firestore's limits. The plan
  therefore keeps Firestore as the transport and adds only an append-only
  event collection plus indexes.

## 8. Platform reach — the hardest constraint

The current source **cannot compile for web**. Evidence is an import census of
unconditional `dart:io` imports in shipped library code:

| File | Why it blocks web |
|---|---|
| `core_app/lib/app_bootstrap.dart:35` | `import 'dart:io'` (boot chain) |
| `core_app/lib/app/config/force_update_guard.dart:1` | store-version checks |
| `core_app/lib/app/compliance/data_export_service.dart:2` | file export |
| `core_app/lib/features/driver/proof_of_delivery_service.dart:2` | photo capture |
| `packages/core/lib/src/cache/isar_service.dart:1` | Isar (no web support) |
| `packages/core/lib/src/error_logger/logger_service.dart:2` | file-backed logs |
| `packages/core/lib/src/kitchen/kitchen_offline_service.dart:3` | Isar-backed offline |
| `packages/core_ui/lib/src/theme/app_theme.dart:2` | `Platform` font selection |

Additional web-hostile dependencies already imported by `core_app`:
`isar_community` (no web target), `workmanager`
(`app/queue_sync_scheduler.dart`, `orders/domain/kitchen_task_dispatcher.dart`),
`firebase_crashlytics`, `flutter_stripe` (web-capable, but the SDK surface
used is the native sheet), `geolocator`, `flutter_map`.

`kIsWeb` guards exist in only four places (`app_bootstrap.dart` ×4,
`force_update_service.dart`, `firebase_options.dart` ×2, `logger_service.dart`),
so the code is not written for a second platform.

**Positive**: `packages/core/lib/src/network/sync_queue.dart` defines
`abstract class SyncQueue` (line 60) with `IsarSyncQueue implements SyncQueue`
(line 80). A web adapter can be added behind the existing interface rather
than rewriting the offline queue call sites.

Conclusion: "iPad web, one codebase" is a **bounded port**, not a build flag —
8 files plus adapters, a web platform folder, and dependency substitutions.
It is a spike-decided item, not an assumption.
