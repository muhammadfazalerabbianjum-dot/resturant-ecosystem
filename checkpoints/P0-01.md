## Two findings that changed the work

1. **The emulator gate was green for the wrong reason.** The command the card
   described (`firebase emulators:exec … "flutter test
   test/firestore_emulator_rules_test.dart"`) proved nothing: that suite builds
   documents with `fake_cloud_firestore` and never contacts the emulator, so
   invalid rules still produced PASS in 32.2s. Gate (d) is now a two-sided REST
   probe (`tool/rules_probe.mjs`: `/menus` must be 200, `/users` must be 403) and
   fails on broken rules in 11.4s. Recording the mock suite as a gap is P0-4's
   job; the gate no longer hides it.
2. **`gate.cmd` cannot be invoked bare on this machine.** `%NoDefaultCurrentDirectoryInExePath%`
   is `1`, so `cmd /c "gate.cmd check"` fails with *not recognized*; `.\\gate.cmd`
   and the absolute path both work. Documented as D-006 so an orchestrator does
   not conclude the tool is missing.

## Post-run amendment (gate f scope)

The green run above scanned 7 files. While reviewing it I found that
`git status --porcelain` collapses an all-new directory to `?? tool/`, so files
inside a newly created folder were never scanned — the shape every future card's
work takes. Changed to `git status --porcelain -uall` and re-ran only the affected
gate: `gate-20261108T172555Z`, `[f] stub-scan PASS (10 file(s) scanned)`, exit 0 —
the count correctly grew from 7 to 10 (three `tool/*.mjs` files joined the seven
tagged tests) and the verdict held, which also shows the runner's own
concatenated-marker trick works now that it is genuinely in its own scan scope.
Gates (a)–(e) were unchanged by this edit (config untouched) and their PASS
results from `20261108T171011Z` stand.
