# P1-5 — Claims: `tenantId`, `roles[]`, `branchIds[]`, revocation — DONE

## Deliverable

- `core_app/functions/src/claims.ts` — `buildUserClaims` is the ONE function that
  turns a `users/{uid}` document into custom claims: `tenantId`, `roles[]`
  (authority, de-duplicated, validated against the P1-1 role table),
  `branchIds[]` (sorted), `claimsVersion`, plus the legacy single `role` only
  when it is unambiguous. An unknown role, a blank tenant or a malformed branch
  list throws `ClaimsValidationError` — no guessed claim.
- `planClaimSync(before, after)` — decides what the trigger writes. Authority
  changes (roles, branches, tenant) bump `claimsVersion` and set `revoke: true`;
  cosmetic edits do neither; a user left with no roles gets `claims: null`.
- `core_app/functions/src/index.ts` — `syncUserRoleClaims` now writes the shaped
  claim document and calls `revokeRefreshTokens` when authority changed. The
  edit is net-neutral in size (the old `if (role) … else …` block was replaced).
- `core_app/functions/src/access.ts` — `assertCapability` takes an optional
  `{claimsVersion}` freshness requirement. When supplied, a token minted before
  the caller's last privilege change is denied with reason `stale_claims`, which
  maps to `permission-denied`.
- `core_app/functions/test/claims.test.js` — C-1…C-6, S-1…S-3.

The card's two assertions:

- **Claim shape** — C-1 asserts `tenantId`, `roles: ['counter','waiter']` and
  sorted `branchIds` on the minted claims; C-2 asserts the legacy single role
  still authorises and that `roles[]` wins when both shapes exist (the migration
  shape); C-3 asserts the fail-closed cases.
- **A stale claim cannot pass after revocation** — S-1: a token carrying
  `claimsVersion: 3` is denied `payment.refund` when the gate is told to require
  version 4, with reason `stale_claims` and code `permission-denied`. S-2: a
  fresh token passes, a token with no version counts as stale, and the check is
  opt-in so P1-1's contract is unchanged for callers that do not pass it. S-3:
  freshness cannot rescue an ungranted capability.

## Decisions recorded

D-032: claims are built by one function from the user document; `roles[]` is
authority and `role` is a derived legacy value minted only when unambiguous; any
authority change bumps `claimsVersion` AND revokes refresh tokens; the gate's
freshness check is opt-in so it ships without breaking existing call sites.

## Deployment ordering risk (IMPORTANT, must be honoured)

The trigger now refuses to mint claims for a user document without `tenantId`
(it returns `claims: null`). **Today's user documents have no `tenantId`.** So
deploying this trigger before the `migrate_v004_tenancy` backfill (P1-6) would
strip every staff member's claims on their next profile write — fail-closed, not
a privilege escalation, but a staff lockout. Order is therefore fixed: backfill
first, then the trigger. Recorded here and in D-032 so it cannot be lost.

## Known gaps (explicit)

1. No callable passes `{claimsVersion}` yet; P1-4/P1-6 will read the version from
   the user document at the call site. Until then the freshness check is proven
   by unit test but unused in production paths.
2. `tenantIds[]` (membership in the shared project) is deliberately NOT a claim:
   the token carries the ACTIVE tenant, and membership is checked server-side at
   sign-in (handoff §8.3 keeps the user pool shared).
3. `revokeRefreshTokens` is wired but cannot be exercised without a real Auth
   project — the emulator has no Auth trigger lane in gate (d). The decision that
   drives it is fully unit-tested; the call itself is one line of SDK usage.
