# P1-1 — Capability table + server gate — DONE

## Deliverable

- `core_app/functions/src/permissions.ts` — pure role → capability table,
  `ROLES`, `CAPABILITIES`, `grantsFor`, `can`, `canAny`. No imports, so the
  compiled module is testable without firebase-admin.
- `core_app/functions/src/access.ts` — `assertCapability(auth, capability)` and
  `capabilityDenialCode(result)`; reads the `roles[]` claim with the legacy
  `role` claim as fallback, fails closed on every malformed shape.
- `core_app/functions/src/index.ts` — `dispatchToFleet` now gates on
  `fleet.dispatch` instead of "any staff role". Behaviour is unchanged today
  (all four existing staff roles hold it); the seam is what changes.

  `capability_not_granted`, mapped by `capabilityDenialCode` to
  `permission-denied`, while the same caller keeps `table.open`.

## What this does and does not prove

- Proves: the server vocabulary can express all six roles plus `delivery`; one
  table decides, one gate enforces, malformed claims fail closed, and a waiter
  cannot take money even if the client asks.
- Does **not** prove: end-to-end denial at a POS callable (that surface does not
  exist until Phase 2). The mapping is asserted at the gate, which is the layer
  every future staff handler will call.
