The card's assertion — **a second run changes zero documents** — is asserted
twice, at both layers:

- **Planner** (M-2, M-5): the plan's own output is fed back through the planner,
  which must emit `writes: []`, and the re-applied documents must deep-equal the
  first run's.
- **Wrapper** (M-8, M-10): with a fake Firestore, the first `apply` records one
  batch commit; the second `apply` records **no additional commit at all**
  (`db.commits.length` unchanged) and reports `planned: 0, applied: 0`.

Dry-run proof: M-7 and M-10 run the wrappers with `apply: false`, assert the plan
is reported (`planned: 2` / `planned: 1`), and assert `db.commits.length === 0`
and that the documents still have no `tenantId`/`roles`.

Conflict proof: M-3 and M-9 seed a document owned by `other-client`; it is
reported as a conflict and is **not** written, while its neighbour is. A blank
target tenant throws `MigrationConflictError`.

## Known gaps (explicit)

1. The migrations have never been run against a real project — that is
   human-only (A2) and needs credentials this repo must not carry. What is proven
   here is the planning logic and the wrapper's dry-run/idempotency against a fake
   store, not a live Firestore run.
2. `planTenancyBackfill` fetches each collection's documents with a full
   collection read. Correct for today's data size; a paginated read is needed
   before this is run against a large production collection.
3. Deploy ordering (unchanged from D-032/Q-004): v004 must run **before** the P1-5
   claims trigger and before the P1-4 rules.
