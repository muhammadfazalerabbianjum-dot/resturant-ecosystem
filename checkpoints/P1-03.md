# P1-3 — Reversal + rollups — DONE

## Deliverable

- `core_app/functions/src/ledger.ts` (+ `buildReversalRow`, `appendReversal`,
  `reversalDocId`) — a reversal is a **new** row (`rev_<originalRowId>`,
  deterministic, so a retried refund cannot double), with every amount mirrored
  and negated. `appendReversal` only ever `tx.set`s the reversal; the original is
  read and never written, so "byte-identical afterwards" is structural.
- `core_app/functions/src/rollups.ts` — `computeRollup` is pure;
  `rebuildDailyRollup` recomputes one branch-day and compare-and-sets the cache
  document on `version`. A rollup document is a pure function of the ledger rows
  passed in; nothing here reads a rollup to decide ledger content.
- `core_app/functions/test/reversal_rollups.test.js` — both halves of the card in
  one file, as the card's DONE-WHEN requires.

The two claims, verbatim from the run:

- **R-3** — the original row is byte-identical after the reversal: the test
  compares `JSON.stringify` of the stored sale row before and after, and
  asserts the store holds exactly two documents (the sale, untouched, and the
  reversal).
- **U-1** — the rollup equals a from-scratch rebuild: the cache is seeded with a
  deliberately wrong, stale document (`revenueByChannel: {web: 999999}`,
  `ordersCount: 42`, `version: 7`); after the rebuild the stored totals deep-equal
  `computeRollup(rows)` computed independently, and the version is 8.

Supporting cases: R-2 (missing original refused, nothing written), R-4 (replayed
reversal returns `kept`, store still holds two documents), R-5 (non-sale / zero /
non-numeric originals refused, blank reason refused), U-2 (a reversal never
erases a sale from `ordersCount`; refunds are reported separately; a row with no
channel lands in `unknown`), U-3 (empty day is all zeros; version only moves
forward), U-4 (bad ids and bad rows fail closed).

## Decisions recorded

D-031: reversal ids are `rev_<originalRowId>`; refunds are a separate
`refundsCents` figure and also subtract from `revenueByChannel`, so gross sales
per channel stay readable next to what was refunded. Reversal rows copy the
original's `branchId`/`channel`/`currency` rather than accepting them from a
caller.

## Known gaps (explicit)

1. Nothing calls `appendReversal` yet — the staff `reverseTransaction` callable
   is Phase 2 (`staff_orders.ts`, handoff §9.3). This card proves the ledger and
   rollup layer, not its authorization; the capability gate is exercised by the
   Phase 2 callable.
2. `topItems` and `staffActivity` are absent from the rollup document: sale rows
   carry no item snapshot yet (no surface writes one), so computing them would
   mean inventing data. They land with the Phase 2 POS rows.
3. The rollup rebuild takes its rows from the caller; the production caller must
   query the ledger by `branchId` + day. There is no Firestore query wrapper in
   this card by design (the module stays testable and the query belongs to the
   callable that schedules it).
4. `channel` is still `unknown` for today's customer path (D-030), so a rollup
   built now would show one channel bucket. That is honest, not broken.
