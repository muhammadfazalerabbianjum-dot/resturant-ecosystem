# P0-5 — Rules parity gate — DONE

Deliverable: `core_app/tool/check_backend_parity.dart` plus gate (h) in
`gate_config.json`. No rule or index content was changed.

## What it checks

For every `apps/*/backend/` directory, these three files must be byte-identical
to the canonical copy in `core_app/`:

- `firestore.rules`
- `storage.rules`
- `firestore.indexes.json`

Missing target file counts as divergence. The script exits `0` clean, `1` on
divergence, `2` on bad input (unknown flag, missing canonical source, or **no
backends found at all** — with nothing to compare, "no divergence" would be a
green gate that checked nothing).

`--fix` copies the canonical file over each divergent/missing target — the
`--refresh-backend` half the card asks for — and re-running it is a no-op.

Before the plant all three files were already identical, so the gate started
green for a real reason rather than by accident. The planted divergence was
removed by `--fix`, not by `git checkout`, which also proves the refresh path.

## Choice of mechanism (D-011)

The card offered "Dart test or generator flag `--refresh-backend`, your call".
Implemented as a standalone Dart script run directly by gate (h)
(`dart run tool/check_backend_parity.dart`, ~1–2s) rather than a `flutter test`
file (~30–60s of harness startup for three file comparisons) and rather than a
flag on the 4,800-line generator, whose argument parsing is shared with real
client generation and would need dry-run plumbing to avoid writing a client.

## What this does NOT prove

Parity is a *consistency* check, not a *correctness* check: it cannot tell
whether `core_app/firestore.rules` itself is right, and it says nothing about the
rules that are actually deployed to any Firebase project (that needs a
deployment, which P0 forbids).
