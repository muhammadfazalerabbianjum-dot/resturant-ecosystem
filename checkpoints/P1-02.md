# P1-2 — Ledger: one row per order, atomically — DONE

## Deliverable

- `core_app/functions/src/ledger.ts` — `buildSaleRow` (pure shape + validation),
  `ledgerDocId` (deterministic `sale_<orderId>`), `decideLedgerWrite`
  (append/keep), `commitOrderWithLedger` (order + row in one
  `runTransaction`), `commitSaleForOrder` (the `createOrder` entry point; every
  row field except the payment facts is read from the order document being
  written, so the two cannot disagree).
- `core_app/functions/src/index.ts` — `createOrder` now commits through
  `commitSaleForOrder` instead of `orderRef.set(storedOrder)`. One call site,
  three lines; the money values are the charged `PaymentIntent.amount` and its
  currency, never client fields.
- `core_app/firestore.rules` — `match /transactions/{rowId}`: owner-only read,
  `allow write: if false` for every caller.
- `core_app/test/security/tenant_isolation_cases.json` — `transactions` row
  (PENDING-TENANCY with a reason; P1-4 activates it).
- `tool/ledger_probe.mjs` + `tool/rules_probe.mjs` — gate (d) now proves the
  ledger against the real emulator, not just its pure functions.

## Decisions recorded

D-030: ledger row id is `sale_<orderId>`; rows are append-only; the row is
written inside the order's transaction; amounts and currency come from the
charged PaymentIntent; `channel` is **not** recorded yet (the order document does
not carry one) — P1-3's rollups and Phase 2's counter surface will need it, and
that is named as the narrowing step.

## Known gaps (explicit)

1. `channel` is absent from the row until a surface supplies it (Phase 2 POS).
   Rollups by channel (P1-7) will therefore only cover what exists by then.
2. Reversals are not written yet — that is P1-3.
3. Only the customer `createOrder` path writes a row; no staff path exists yet
   (Phase 2).
4. Gate (d) covers the transaction semantics; it does not re-run the full Stripe
   verification path, which is P0-tested elsewhere.
