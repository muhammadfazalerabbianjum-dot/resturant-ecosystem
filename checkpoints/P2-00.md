## 5. Recommendation (the ruling is the owner's)

**Take the A8 fallback: a thin shell that reuses the service layer, not a
Flutter-web port.** The measured trigger in D-023 — "if goldens/boot gates
cannot run on web" — is met twice over: the boot does not compile, and the
golden suite is web-incompatible regardless of the build.

Cost of each route, from the evidence above:

**A. Keep Flutter web — three structural changes before the first screen runs**
1. **Cache seam.** Replace the barrel export + 4 consumers with an interface and
   conditional imports (`if (dart.library.js_interop)`) plus a browser
   implementation. The offline order queue (`sync_queue`) and its dead-letter
   behaviour are the hard part: an IndexedDB implementation has to preserve the
   ordering and DLQ semantics that today's tests pin on Isar. This is an
   architectural change (SUPERVISED under the constitution), not a card-sized
   edit.
2. **Money renderer portability** — the two int64 sentinels above, with the
   full money parity matrix re-run.
3. **App Check on web.** D-036 binds tenancy to the verified App Check app id.
   A web client needs a registered web app plus an App Check web provider
   (reCAPTCHA family); without it every tenant-gated write is denied. That is a
   Firebase-console action and a new app registration — owner/human side.
   And the golden suite would still not run on web, so the visual gate would
   have to be re-founded, which is exactly the cost A8 named.

**B. Thin shell reusing the Isar-free service layer** — no native database in
the bundle, boot/FMP measurable immediately; the shell re-renders the staff
surfaces it needs (counter/POS, kitchen, waiter) so **no Flutter golden is
reused**, and it must not fork business logic (D-023). It also needs the same
web App Check registration as A.3, but nothing in `packages/core`'s native
layer blocks it.

Both routes need the web App Check registration. Only A needs the cache seam
before the first pixel.

**Ownership note for the ruling:** if the shell must queue orders offline, the
cache seam (A.1) is a shared prerequisite either way; if the counter surface may
require connectivity, B ships without it.

## 8. Pre-work verification for P2-1a item 2 — the portable min-int predicate

Done on 2026-11-13 before P2-1a relies on it, and reverted afterwards so the
card still owns the change. Nothing below is a claim about code that is in the
tree now; it is a measurement of the predicate the card will use.

### The predicate

`bool isMinInt(int v) => v != 0 && v == -v;` — chosen because it is the same
source text on both targets, unlike the literal it replaces.

### VM truth table (`dart run` on a 6-row probe)

| value | `-v` | `-v == v` | predicate |
| --- | --- | --- | --- |
| minInt64 (−9223372036854775808) | −9223372036854775808 (wraps) | true | **true** |
| minInt64 + 1 | 9223372036854775807 | false | false |
| −1 | 1 | false | false |
| 0 | 0 | **true** | **false** |
| 1 | −1 | false | false |
| maxInt64 | −9223372036854775807 | false | false |

The `v != 0` clause is load-bearing: `0 == -0` would otherwise make zero the
second "min int". With it, the predicate is true for exactly minInt64.

### Web truth table (`dart compile js -O2` then `node`)

| value | predicate |
| --- | --- |
| −2^52 | false |
| 2^52 | false |
| −1, 0, 1 | false |
| 2^53−1 (largest exact int on web) | false |

The probe cannot even *express* minInt64 on web — `dart compile js` rejects the
literal `9223372036854775807` with the same error P2-0 hit, which is the point:
the value does not exist there, so a false predicate is correct, not a gap.

### Against the existing money parity tests (predicate applied, then reverted)

With both guard sites rewritten to the predicate:

```
core_app: money_fail_closed + money_cldr_parity + money_byte_identity + money_krw_rule
  00:05 +50: All tests passed!          CORE_APP_MONEY_EXIT=0
packages/core_ui: test/money_cldr_test.dart
  00:00 +8: All tests passed!           CORE_UI_MONEY_EXIT=0
```

Both int.min assertions still pass by name — `int.min fails closed to the T-5
placeholder in BOTH locales` (parity) and `int.min yields the placeholder —
never fabricated digits` (core_ui). So the parity matrix does cover the guard,
and the predicate is behaviour-equivalent on the VM for everything it covers.

**What this does not prove:** no web run exercises the guard, because no web
value can reach it; and the JS probe compiles the predicate in isolation, not
the money renderer itself. P2-1a's build is the first test of the latter.

**Files touched and reverted:** `packages/core_ui/lib/src/ui/money_text.dart`,
`core_app/lib/app/config/currency_format.dart` (both restored to `_kMinInt` /
`_kMinCents`; `grep` re-confirms). Temporary probes deleted.
