# P0-11 — Processor adapter (pure refactor) — DONE

`createChargeIntentCore` now calls a `ProcessorAdapter`; the Stripe implementation
contains the exact params literal that used to sit at the call site.

## The seam

`core_app/functions/src/payments/processor_adapter.ts`:

- `ProcessorAdapter` — `processor` identity + `createIntent(request)`.
- `CreateIntentRequest` — amount (cents), currency, metadata, optional
  `receiptEmail`, idempotency key. Typed, so the adapter cannot invent money.
- `StripeProcessorAdapter` — calls `paymentIntents.create` with the same four
  params, in the same order, with the same `automatic_payment_methods`, the same
  conditional `receipt_email`, and the same `{idempotencyKey}` option.

**What did not move**: menu re-pricing, tax/promo resolution, delivery-fee clamp,
amount computation and `buildChargeIntentMetadata` all stay in the core. The
adapter moves money; it does not decide how much. That split is what keeps this a
refactor rather than a rewrite.

`input.stripe` (the existing injection seam the emulator harness uses) is
unchanged — the adapter wraps whatever Stripe-like object arrives, so
`CreateChargeIntentStripeSeam` remains the public contract.

## Diff shape
